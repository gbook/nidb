# NiDB — NIST SP 800-171 Compliance Analysis

**Status:** Draft for internal review
**Date:** 2026-07-27
**Baseline used:** NIST SP 800-171 **Rev 2** (110 requirements, 14 families), with Rev 3 deltas noted
**Companion document:** [`21-cfr-part-11-gap-analysis.md`](21-cfr-part-11-gap-analysis.md) — overlaps heavily on audit trail and authentication

---

## 1. Applicability — read this first

NIST SP 800-171 protects **Controlled Unclassified Information (CUI)** in **nonfederal** systems. It
applies to NiDB **only if** the data NiDB holds is CUI. That determination is made by the federal
sponsor/contract, not by this document, and it is the first thing that must be settled:

- **If the awarding agency designates the research data as CUI** (common CUI categories that fit NiDB:
  *Privacy → Health Information*, *Research*, and for DoD-funded work *Controlled Technical
  Information*), 800-171 applies to the enclave NiDB runs in.
- **If not**, 800-171 is not binding, though it remains a reasonable hardening target and most of the
  gaps below are ordinary security debt regardless.
- **Contract vehicle matters.** DFARS 252.204-7012 and **CMMC Level 2** assessments currently key to
  **Rev 2's 110 requirements**; the DoD transition to Rev 3 is expected but should be confirmed
  against the contract before choosing a baseline. NIH/other-agency CUI flow-downs may cite Rev 3
  directly. **This document uses Rev 2 numbering** because that is what an assessor is most likely to
  score against today.

### Framing: NiDB is a component, not the system

800-171 assesses a **system boundary** — hosts, network, people, and process — not a source tree. Of
Rev 2's 110 requirements, roughly:

| Where the control lives | Count (approx.) | Can NiDB code affect it? |
|---|---|---|
| Organizational / procedural (policy, training, IR, personnel, physical) | ~35 | No |
| Infrastructure / OS / network (hypervisor, firewall, EDR, NTP, VPN, MDM) | ~40 | No — but NiDB must not obstruct it |
| **Application-level — NiDB code, schema, and installer** | **~35** | **Yes** |

This analysis therefore has two jobs:

1. **Score and remediate the ~35 application-level requirements** that NiDB genuinely owns.
2. **Document what NiDB requires of the hosting enclave**, so the System Security Plan (SSP) can
   inherit those controls and NiDB's defaults don't silently break them.

Marked throughout: **[CODE]** (NiDB source/schema/installer), **[INFRA]** (hosting environment),
**[PROCESS]** (organizational), **[BOTH]**.

> **This is a technical gap analysis, not a compliance determination and not legal advice.** An
> authorizing official / ISSO must own the SSP, the POA&M, and the final assessment.

## 2. Executive summary

**NiDB as shipped today cannot be placed in an 800-171 CUI enclave without significant remediation.**
The blocking issues are not exotic — they are foundational:

| # | Blocker | Requirements implicated | Effort |
|---|---|---|---|
| **P0-1** | **Default credentials baked into the installer.** MariaDB `root` and the `nidb` DB user are both set to the literal password `password`, granted `ALL PRIVILEGES ON *.*` from **any host** (`'nidb'@'%'`); the OS `nidb` account is created with password `password`. | 3.5.2, 3.5.7, 3.5.10, 3.1.1, 3.1.5, 3.4.2 | Low |
| **P0-2** | **No TLS anywhere.** The installers open port **80 only** — no 443, no `mod_ssl`/certificate provisioning in either RPM or Debian post-install. Credentials and CUI cross the network in cleartext. | 3.13.8, 3.13.11, 3.13.15, 3.1.13, 3.5.10 | Low–Med |
| **P0-3** | **Broken password storage.** Unsalted `sha1()` (`login.php:250`, `adminusers.php:142`/`:299`, `users.php:124`, `register.php:162`/`:353`, `publicdownloads.php:68`). The `users.password` column is `varchar(45)` — **too narrow to hold a bcrypt (60 char) or argon2id (~95 char) hash**, so a schema migration is a prerequisite. | 3.5.10, 3.5.2 | Med |
| **P0-4** | **No security audit trail.** `changelog` is effectively unused, has a **mutable** timestamp (`ON UPDATE current_timestamp()`), and records no before/after values. `audit_results` is a **data-QA** table, not a security log. No logging of reads, exports, or downloads. The app DB user's `ALL PRIVILEGES` grant means audit rows cannot be made append-only. | 3.3.1, 3.3.2, 3.3.6, 3.3.8, 3.3.9 | **High** |
| **P0-5** | **No MFA.** Nothing in the codebase implements a second factor. 3.5.3 is a hard requirement for privileged accounts (local *and* network) and for network access by non-privileged users — it is one of the most common CMMC failure points. | 3.5.3, 3.5.4 | Med–High |
| **P0-6** | **No encryption of CUI at rest.** `archivedir` is plain filesystem storage; `moduleBackup.cpp` contains **no** encryption (grep for `encrypt`/`gpg`/`openssl enc` → zero hits), so backups/tape leave the boundary unprotected. | 3.13.16, 3.8.9, 3.8.6 | Med (infra-assisted) |
| **P0-7** | **Systemic injection & access-control defects.** SQL injection (remediation in progress, string-field pass and admin pages outstanding), `getfile.php` path traversal + IDOR, missing ownership checks in `ajaxapi.php`, shell injection via `SystemCommand()` (`sh -c`) in the C++ modules. | 3.14.1, 3.13.2, 3.1.1, 3.1.2 | **High** |

**The good news:** NiDB already contains a **modern reference implementation** of much of what is
needed. `api2.php` does token auth with `password_verify` (argon2id → bcrypt fallback), stores only a
SHA-256 hash of the session ID, enforces a **10-minute idle timeout**, **throttles brute-force by
IP**, forces POST-only so secrets stay out of logs, and records attempts to `remote_logins`. The
per-project RBAC schema (`user_project`: `project_admin`, `view_data`, `view_phi`, `write_data`,
`write_phi`) is also already the right shape. Most of the auth work is **extending existing patterns
to the web tier**, not inventing them.

## 3. Family-by-family assessment

Legend: ✅ met · ⚠️ partial · ❌ gap · ➖ not NiDB's control (inherit from enclave)

### 3.1 Access Control (22 requirements)

| Req | Control | Status | Basis |
|---|---|---|---|
| 3.1.1 | Limit access to authorized users/processes/devices | ⚠️ **[CODE]** | Login + session guard exist (`includes_php.php` — the missing-`exit()` fragility noted in the 2026-07 pentest **is now fixed**). Undermined by IDOR (`getfile.php?fileid=`, `ajaxapi.php` update actions accept IDs with no ownership check), default DB creds reachable from `'%'`, and unauthenticated DICOM ingest on 104/8104. |
| 3.1.2 | Limit access to authorized transactions/functions | ⚠️ **[CODE]** | `isAdmin()` gates admin pages; per-project RBAC exists in `user_project` but is **thinly enforced** — `view_phi` appears in only ~24 places across 8 files. Authorization is per-page and ad hoc, not centralized. |
| 3.1.3 | **Control the flow of CUI** | ❌ **[CODE]** | Multiple egress paths with no flow control or logging: export (`moduleExport`, squirrel/BIDS/NDA), `getfile.php`/`download.php`, remote connections (`remoteconnections.php`), and **public datasets/downloads** (`publicdatasets.php`, `publicdownloads.php`, `pd.php`). | 3.1.4 | Separation of duties | ❌ **[BOTH]** | Single `user_isadmin` superuser role; no split between e.g. system admin, security/audit admin, and data steward. |
| 3.1.5 | Least privilege | ❌ **[BOTH]** | DB grant is `ALL PRIVILEGES ON *.*`. Data directories are created **world-readable** (`mkdir -m 764 /nidb/data/...`, `-m 774 /nidb`). Admins get all-or-nothing. |
| 3.1.6 | Non-privileged accounts for nonsecurity functions | ➖ **[PROCESS]** | Enclave/OS practice. NiDB should support a separate admin login rather than an "admin flag on my daily account". |
| 3.1.7 | Prevent non-privileged users executing privileged functions; **log attempts** | ❌ **[CODE]** | No logging of authorization denials anywhere. |
| 3.1.8 | **Limit unsuccessful logon attempts** | ❌ **[CODE]** | Web `login.php` has no lockout or throttle. `api2.php` **does** throttle by IP — port that pattern to the web login and add account lockout. `remote_logins` already stores success/failure per IP, so the data is available. |
| 3.1.9 | **System use notification** (privacy/security banner) | ❌ **[CODE]** | No banner on `login.php`. Trivial to add; assessors check it. |
| 3.1.10 | Session lock with pattern-hiding display | ➖ **[INFRA]** | OS screen lock. |
| 3.1.11 | **Terminate session after inactivity** | ❌ **[CODE]** | No idle or absolute timeout on the web session; `session_start()` in ~50 pages with **no** `session_set_cookie_params` and no `session_regenerate_id`. Only `api2.php` expires sessions (10 min idle). |

| 3.1.16–3.1.19 | Wireless, mobile devices | ➖ **[INFRA]** | Out of NiDB's control. |

Credentials are stored as `sha1('$remotepassword')` (`remoteconnections.php:99`/`:121`) — a **one-way hash used where a usable credential is needed**, which is a design defect on its own. No allowlist of permitted peers. |
| 3.1.21 | Limit portable storage on external systems | ➖ **[PROCESS]** | |
| 3.1.22 | **Control CUI posted on publicly accessible systems** | ❌ **[CODE]** | `publicdatasets.php` / `publicdownloads.php` / `pd.php` publish data with `sha1`-based link tokens. With no CUI designation in the data model, **nothing prevents CUI being published**. Needs a hard interlock. |

Entirely organizational (3.2.1–3.2.3). Note only that NiDB administrators and pipeline authors need

### 3.3 Audit and Accountability (9) — **the largest code gap**

| Req | Control | Status | Basis |
|---|---|---|---|
| 3.3.1 | Create/retain audit logs sufficient to investigate unauthorized activity | ❌ **[CODE]** | Only `remote_logins` (login success/failure) is real. **No** record of data reads, exports, downloads, permission changes, or record modifications. |
| 3.3.2 | **Uniquely trace actions to individual users** | ❌ **[CODE]** | `changelog` carries `performing_userid`/`performing_username` but is essentially unpopulated (4 `insert into changelog` sites). The **C++ modules act as a service account** with no end-user attribution at all. |
| 3.3.3 | Review/update logged event types | ❌ **[PROCESS]** | No defined auditable-event list. |
| 3.3.4 | Alert on audit logging failure | ❌ **[BOTH]** | Silent failure today. |
| 3.3.5 | Correlate audit review/analysis across the system | ❌ **[BOTH]** | No forwarding to syslog/SIEM. NiDB should emit to syslog so the enclave SIEM can correlate. |
| 3.3.6 | Audit reduction and report generation | ❌ **[CODE]** | No security-audit review UI. (`adminaudits.php` is a **data-quality** viewer over `audit_results` — easily mistaken for this control; it is not.) |
| 3.3.7 | Authoritative time source | ⚠️ **[BOTH]** | Timestamps come from DB `now()`/server clock. Enclave must run chrony/NTP (**[INFRA]**); NiDB should record UTC and note the source. |
| 3.3.8 | **Protect audit info from modification/deletion** | ❌ **[BOTH]** | `changelog.change_datetime` is `ON UPDATE current_timestamp()` — rows are silently mutable. The app DB user holds `ALL PRIVILEGES`, so it can `UPDATE`/`DELETE` audit rows. **Blocks the control outright.** |
| 3.3.9 | Limit audit management to a privileged subset | ❌ **[BOTH]** | No audit-administrator role distinct from `user_isadmin`. |

> **Design note:** 3.3.1/3.3.2 plus §11.10(e) of the Part 11 analysis are the *same build*. Do it once.
> Because writes are scattered across ~122 PHP files **and** the C++ backend, the hybrid approach is
> the realistic one: **DB triggers** on in-scope tables for guaranteed coverage, plus a per-connection
> session variable set at request start so the trigger can attribute the change to the end user.
> Reads/exports must be logged at the application layer (triggers can't see them).

### Rev 3 deltas (if the contract cites Rev 3)
Rev 3 restructures to **97 requirements across 17 families** and adds three that NiDB touches:
- **3.15 Planning** — system security plan and rules of behavior (**[PROCESS]**).
- **3.16 System and Services Acquisition** — external system services, **security engineering principles** (reinforces 3.13.2).
- **3.17 Supply Chain Risk Management** — NiDB's vendored JS, Qt/DCMTK/bit7z bundling, and pipeline
  dependencies become explicit obligations; an **SBOM** is the practical deliverable.
Rev 3 also withdrew some Rev 2 requirements and folded in tailored controls (notably around
organization-defined parameters). None of the P0 items above changes under Rev 3.

## 4. Remediation roadmap

Sequenced so that each phase unblocks the next and so overlapping Part 11 obligations are paid once.

### Phase 0 — Stop shipping insecure defaults *(days; do immediately)*
1. **Remove all default credentials** from `rpm_post_install.sh` / `deb_post_install.sh`: generate
   random passwords, or fail the install and require them to be supplied. **[CODE]**
2. **Scope the DB grant.** Replace `GRANT ALL PRIVILEGES ON *.* TO 'nidb'@'%'` with per-table
   privileges limited to `localhost`/the app host. Prerequisite for 3.3.8. **[CODE]**
3. **Tighten data directory modes** — remove world access (`0764`/`0774` → `0750`). **[CODE]**
4. **TLS by default:** provision certs, enable 443, redirect 80, set HSTS; open 443 not 80 in the
   firewall stanza. Restrict 104/8104 to enumerated modality hosts. **[CODE]/[INFRA]**
5. **Session cookie hardening:** `session_set_cookie_params` with `HttpOnly`, `Secure`, `SameSite=Lax`
   in one shared include; `session_regenerate_id()` on login. **[CODE]**
6. Add the **3.1.9 system-use notification banner** to `login.php`. **[CODE]**

### Phase 1 — Authentication and access control *(weeks)*
7. **Decide the FIPS question first** (3.13.11) — it determines the hashing algorithm.
8. Widen `users.password` (and `users_pending.password`) beyond `varchar(45)`, then migrate SHA1 →
   `password_hash()` with transparent rehash-on-login. Reuse the `api2.php`/`adminusers.php:260`
   pattern. Remove `sha1(password)`-as-credential from `api.php`. **[CODE]**
9. **Port `api2.php`'s controls to the web login:** failed-attempt throttle + account lockout (3.1.8),
   idle **and** absolute session timeout (3.1.11/3.13.9). **[CODE]**
10. **Integrate SSO/OIDC for MFA** (3.5.3/3.5.4) — add an `SSO` `login_type`. Also delivers password
    policy, history, and reuse prevention (3.5.5–3.5.9) via the IdP.
11. **Centralize authorization.** Build one enforcement helper over `user_project`
    (`view_data`/`view_phi`/`write_data`/`write_phi`/`project_admin`) and route every page through it —
    this is what closes 3.1.1/3.1.2/3.1.5 and the IDOR findings together. Split `user_isadmin` into
    distinct roles for 3.1.4/3.3.9. **[CODE]**
12. **Fix the known defects:** `getfile.php` traversal (`realpath()` containment) and IDOR (ownership
    check), finish the SQLi sweep (string fields, identifier whitelisting, admin pages), add CSRF
    tokens, fix the unauthenticated `setup.php`/`system.php` config-absent path. **[CODE]**

### Phase 2 — Audit and accountability *(the big build; months)*
13. **Design doc first** (shared with Part 11 §11.10(e)): enumerate in-scope tables, choose
    hybrid triggers + app-layer, define an **append-only before/after schema**.

18. Build an **admin audit review/export UI** (3.3.6) — distinct from `adminaudits.php`, which is the

## 7. Caveats

- **Technical gap analysis only** — not a compliance determination, certification, or legal advice.
  An authorizing official/ISSO owns the SSP, POA&M, and assessment.
- **800-171 applies to a system boundary, not a source tree.** Even a fully remediated NiDB is only
  compliant inside a compliant enclave; roughly two-thirds of the 110 requirements are not NiDB's.
- **Applicability is unresolved.** If the data is not CUI, none of this is binding — but the P0 items
  are security debt worth fixing on their own merits.
- **Heavy overlap with the Part 11 analysis.** Audit trail, password storage, session controls, and
  retention appear in both; scope and build them once against the stricter of the two.
- **File:line citations reflect the repository at this date** and will drift. Statements about the
  live deployment (PHP version, DB grants, directory modes) are from the installer scripts and prior
  assessment notes, **not** from inspecting the production host — verify them in situ before relying
  on them for the SSP.
- **No live database or production host was inspected** in preparing this document.
